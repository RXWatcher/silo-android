### R1 — D6's skip-compensation branch returns without draining the settlement `HIGH · regression`
`androidTvApp/.../player/TvSubtitleTransactionAdapter.kt:1532`
*Impact*: after a subtitle change whose publication confirm loses the lifecycle race, the subtitle HUD sticks on "Applying…", the committed-subtitle checkmark shows the previous track while the new one is on screen, the choice is never persisted, and the adapter's `resetAfterSettlement` is stranded pointing at a dead session — later picked up by an unrelated settlement (exactly the leak D8 was written to close). *Mechanism*: verified at :1531-1536 — `if (settlement.mountedIdentity == owner.identity) { finishSettlement(settlement, true); return@launch }` skips `drainSettledPublication()`, `invalidateLocalMount()`, `transition = currentOwner.proposedState` and `persist()`. *Fix*: in the skip branch do everything the `confirmed` branch does except the confirm — `transition = currentOwner.proposedState`, `invalidateLocalMount()`, `failureMessage = null`, `drainSettledPublication(owner = currentOwner, confirmed = true, compensating = false)` — then `finishSettlement(settlement, true)`. Do **not** also write `committedOutputRouteGeneration` here: that must be gated on an actual server confirm, not a local mount observation. Separately drive the server publication to a terminal state (retry `confirmCommitted`, else `abandonCommittedPlayback`) rather than leaving it pending.
*Self-healing caveat*: the UI half recovers on the user's next subtitle/audio/quality press (`mutate()` → `requestSupersessionSettlement`), at the cost of rolling back the subtitle that actually mounted.

## 2. REMAINING DEFECTS (not caused today), by severity

### HIGH

**S1 — Both seek paths still address the server by the rendered plan.**
`PlaybackSessionManager.kt:1206` (`reanchorActiveVideoSession`), `:1460` (`recoverActiveVideoSessionAfterSeek`), `:1639` (`adoptSeekRecoveryPlan`).
*Impact*: after a subtitle pick whose mount failed and rolled back — the routine outcome this whole day's work exists to handle — seeks silently do nothing (playhead snaps back with `error = null`, `TvPlayerViewModel.kt:2663-2684`); the explicit "Unable to seek (The failed plan is no longer current)" banner appears only when rollback is disallowed.
*Mechanism*: verified — both builders send `failedPlanId = active.plan.planId` (:1206, :1460) while `revertRenderedPlanKeepingCursor` deliberately leaves the rendered plan behind the server's. D1 taught only `prepareActiveVideoSessionReplan` (:598) to read the cursor. `adoptSeekRecoveryPlan` (:1639) also never *writes* the cursor, so an accepted recovery re-opens the original 409-forever bug.
*Fix*: fix `recoverActiveVideoSessionAfterSeek` (:1460) to read `active.serverPlanCursor?.planId ?: active.plan.planId`, and have `adoptSeekRecoveryPlan` set `serverPlanCursor = ServerPlanCursor(planId = plan.planId, …)`. Do **not** naively point :1206 at the cursor: `seekReanchorMismatch` (:1315-1345) requires the returned planId to equal `active.plan.planId`, so it would convert a 409 into a 502. Either leave :1206 alone or make re-anchor refuse to run while `cursor.planId != plan.planId` and go straight to recovery. Introduce one `serverPlanId` accessor used by all three builders — three call sites, one already forgotten once.

### MEDIUM

**S2 — libass-rendered ASS ignores the playback timeline offset.** `android-shared/.../SiloPlayerFactory.kt:239`.
*Impact*: with a non-zero `timeline_offset_seconds` plan (resume/seek into a transcode), an ASS/SSA sidecar shows the **wrong** dialogue — events from near the start of the file under the current scene — going blank once position passes the last event, while SRT on the same stream is perfect.
*Mechanism*: verified at :237-241 — `wrapRenderers(media3RenderersFactory, subtitleOffsetHolder::getUserOffsetUs)`. Media3-parsed cues are shifted by `getOffsetUs()` = `userOffsetUs − timelineOffsetUs`; libass, which paints ASS itself and emits no cues, is fed the user-only offset.
*Fix*: pass a provider that returns `getOffsetUs()` when the mounted text track is a sidecar artifact (`SubtitleMountResolver.trackIdDenotes` already distinguishes them) and `getUserOffsetUs()` for embedded. Add a `adjustedPositionUs` test with a non-zero timeline offset — `LibassBridgeTimeTest` covers only the user offset.

**S3 — Embedded MKV fonts accumulate in the process-global libass library forever.** `libass-bridge/.../LibassBridge.java:82` (singleton `AssHandler`), `PlayerModule.kt:75` (Koin `single`).
*Impact*: native memory grows monotonically for the process lifetime; anime/typeset MKVs carry 5–30 MB of attachments each. On a Shield this ends as a mid-episode decoder allocation failure or a silent process kill — "the app just dies after a couple of episodes".
*Mechanism*: `Ass.clearFont()` has zero callers in Silo and zero in ass-media/ass-kt; `Ass`/`AssRender`/`AssTrack` free native memory only in `finalize()`. Not amplified by today's work — today's `VideoTrackSelectionCoordinator` change gated the remount behind `isSubtitleMounted`, which strictly reduces re-parse frequency.
*Fix*: **do not** call `handler.getAss().clearFont()` before `setMediaItem` — libass permits `ass_clear_fonts` only once all tracks/renderers on that library are released, and `AssHandler` only nulls Kotlin references on media-item transition; it is a use-after-free risk and is lossy on resume-at-offset mounts. Scope the `AssHandler` per playback session (create in `SiloPlayerFactory.createPlayer`, tear down in `SiloPlaybackService.onDestroy` alongside `player.release()`, dropping tracks/render before deinit), keeping only the ABI/Matroska capability probes on the Koin singleton.

**S4 — Removing a server purges nothing.** `shared/src/androidMain/.../network/AndroidServerRegistry.kt:118`.
*Impact*: removing a server to reclaim space reclaims nothing in-app (the bytes are still deletable from the system Files app); every Room row survives, and because `idFor()` is base64 of the normalised URL, re-adding the same server resurrects its Downloads list, resume positions, cached home/catalog rows, and any pending outbox ops.
*Mechanism*: verified — `remove()` wipes four SharedPreferences token keys and the registry entry, touching no DAO. `DownloadDao.deleteAllForServer`, `DownloadSubscriptionDao.deleteAllForServer` and `DownloadStorage.deleteAllForServer` exist with **zero** production callers; five other tables have no delete-by-server query at all.
*Fix*: purge **after** dropping the entry, on `Dispatchers.IO`, keyed by the now-orphaned serverId — not inside `identityTransitions.changing { mutex.withLock { … } }`, which would serialise every identity mutation behind a multi-GB filesystem operation on Main. The purge must first cancel/await in-flight downloads (reuse the H5 WorkManager cross-check, else a live `DownloadWorker` re-inserts its row) and must exclude `ActivePlaybackFile.fileId` (offline PiP playback). Make it idempotent and re-runnable at startup for any serverId in Room but absent from the registry, which also cleans existing installs.

**S5 — A profile switch kills the outbox retry chain for the scope with queued work.** `android-shared/.../data/sync/SyncEngine.kt:138`.
*Impact*: watched marks, ratings, favourites and resume positions from one profile stop syncing indefinitely after the household switches profile. On a TV that is never relaunched this is permanent and invisible.
*Mechanism*: verified at :133-144 — `remaining` is counted for the scope active at the **end** of the drain; `SyncWorker` turns `remaining > 0` into `Result.retry()`, the only thing keeping the chain alive. A profile switch does not change `activeServerId`, and none of the four `requestSync` triggers fires on a profile switch.
*Fix*: have `OutboxSyncStarter` also drain on profile change — collect `ProfileRepository.profileSwitches` (already published, consumed only by `HomeRealtimeForegroundStarter`) or `registry.activeEntry.map { it?.profileId }.distinctUntilChanged()`. Optionally add `max(drained-scope count, end-scope count)` for the mid-drain race. **Reject** the unscoped `dao.count()` variant: nothing purges rows for removed servers (see S4), so one orphan row makes the chain immortal, and `ExistingWorkPolicy.KEEP` then swallows every new enqueue behind a backoff climbing to WorkManager's 5 h ceiling — stalling sync for the *active* profile.

**S6 — Backoff reorders the outbox, so a retried mark-watched can wipe a newer resume position.** `android-shared/.../data/repository/RoomUserItemStateRepository.kt:171`.
*Impact*: user marks an episode watched while the server is flaky, then resumes it; progress syncs first, the retried watched lands 30 s+ later and clears it. The episode vanishes from Continue Watching on every device while the user is ten minutes in, and local/server diverge permanently for that item.
*Mechanism*: `dueBatch` orders by `nextAttemptAtMs ASC, id ASC`; `recordFailure` pushes a failed op 30 s·2ⁿ into the future, so a newer op enqueued at `nowMs` drains first. The reverse direction is defended (`record(clearPlaybackProgress = true)` → `deletePendingForTargetKind(SET_POSITION)` + `requiresReplay`); this direction has no defence, and the two ops carry different coalesce keys so `countNewerPending` cannot arbitrate. Deterministic, not a race.
*Fix*: in `recordPositionOwned`, in the same transaction, clamp any pending op for the same `(serverId, profileId, targetContentId)` to `nextAttemptAtMs = nowMs`, restoring creation order. **Do not** delete the pending `SET_WATCHED`: that would leave `ContentItemStateEntity.watched = true` locally with no `revertForTerminalOp`, and could delete the deliberately-requeued replay op that the existing `requiresReplay` guard depends on.

## 3. SHIP BLOCKERS

Nothing in this branch has run on a device. The following must be resolved before it goes on the Shield or into a PR.

**Must fix (code):**

## 5. NEWLY AUDITED AREAS

**libass / JNI — DEFECTIVE (two real defects), otherwise sound, never run on a device.** First-ever audit. `libass-bridge` was not touched today, so nothing here is a regression. The bridge itself is careful: the `format.id` `silo-subtitle:<n>` ↔ `substringAfter(":")` mapping survives MergingMediaPeriod's numeric prefixing in every traced combination; the embedded-MKV fallback parser factory is correct against media3 1.10.1; the ABI/LinkageError probes are correct; `adjustedPositionUs` arithmetic matches Media3's 10¹²µs renderer offset; `overlayRef` weak-reference handling is right. The two defects are **S2** (timeline offset never reaches libass) and **S3** (unbounded font accumulation in the process-global ASS_Library). There is no hand-written JNI or C in this repo — the native layer is third-party `io.github.peerless2012:ass-media/ass-kt` 0.4.0, decompiled for this audit; that dependency's lifetime model (native frees only in `finalize()`) is the root of S3 and is not under our control.

**Sync outbox — SOUND at the core, DEFECTIVE at the edges.** The `dirty_operations` machinery is genuinely well built and I found no defect in the parts most likely to be wrong: atomic `claim`, `supersedeOrRecordFailure`, crash-stranded reclaim, coalesce-key scoping (`serverId|profileId|contentId|kind`, consistently built at every production enqueue site), `AuthScopeSnapshot` pinning of every send, the `requiresReplay` machinery, the `countNewerPending` terminal-revert guard, backoff maths, terminal-vs-retriable classification (401 retriable is correct given the interceptor), the ebook monotonic guard, and a batch loop that cannot spin. Both defects are about *scopes that are not the active one*: **S5** (profile switch kills the retry chain) and **S6** (backoff reorders watched vs position). **R7** is nominally a settings-flusher defect but shares the same root: an op queued under one identity sent under another.

**Room migrations — SOUND, with a lifecycle gap and no test.** Machine-diffed every schema pair 1→8 (tables, columns, affinity, notNull, defaults, PKs, indices) against the emitted migration SQL. Every delta in the entire history is purely additive — no nullability tightening, PK change, index drop or rename — which is why every step is legally an AutoMigration. Today's v8 is correct: `SiloDatabase_AutoMigration_7_8_Impl.kt:15-16` emits the two `ALTER TABLE downloads ADD COLUMN … TEXT DEFAULT NULL`, matching `DownloadEntity.kt:79-81`, and `8.json` is genuine compiler output (identityHash `7db9e8f8fef4735ce710bf216f145d7d` matches `SiloDatabase_Impl.kt:85`). The new columns are wired end to end, so the offline quality-label fix is real. `fallbackToDestructiveMigration` appears **nowhere** in the repo — correct, and worth recording as a positive. Index/uniqueness review is consistent between entity, JSON and generated SQL; the `@Insert(REPLACE)` + secondary-unique-index hazard on `downloads` is correctly worked around by `insertIfAbsent`. Two gaps: **S4** (nothing ever purges Room for a removed server) and **zero migration tests despite two comments claiming otherwise** — this chain has never been executed.

**Cast — SOUND except one regression and one half-landed fix.** First-ever audit of both senders and the TV receiver. Sound and verified: the MediaRouter integration (passive/active scan escalation, selector filtering, route publish) is correct and idempotent; the NSD browser's single-resolve serialization and cancellation bookkeeping are careful and correct; the phone's reconnect state machine holds up under `connectionMutex` re-checks and the `reconnectJob === coroutineContext[Job]` finally-guard; the TV's `sessionEpoch` newest-wins arbitration for concurrent TLS handshakes is correct; `SiloCastPlaybackClock`'s optimistic-window logic is correct; the `identityEndJob` → `identityCleanupScope` half of H10 fixes a genuine leak. Defects: **R9** (the `activePlayer == null` gate) and **S8** (`loadError` has no reader). Not reported as findings but noted: non-`@Volatile` `session`/`output` fields in `SiloCastController` while every other cross-thread field there is `@Volatile`; `SiloCastSessionManager.release()` has no caller.
